# Decision Log — Config A Bare Blitzy Baseline Security Audit

**Artifact:** `decision-log.md` (Explainability rule — Rule 1, AAP §0.7.1)
**Companion artifacts:** `findings-config-a.json` (CRITICAL Directive 2), `executive-summary.html` (Executive Presentation rule)
**Scope:** `calcom-monorepo` (a.k.a. `blitzy-cal`) — read-only security audit
**Methodology:** Four-lens native agent analysis (data-flow, call-chain, configuration, dependency declaration)
**Audit mode:** REFERENCE only — zero source modifications

This document is the single source of truth for every non-trivial decision made during the Config A audit. Per the Explainability rule, a decision is non-trivial if a competent engineer could reasonably have chosen differently. No rationale is embedded in source code comments; all "why" answers live here.

## Section 1 — Process and Methodology Decisions

| Decision | Alternatives | Why | Risks |
|---|---|---|---|
| Treat the audit as strictly read-only — zero modifications to `apps/**`, `packages/**`, `scripts/**`, `.github/**`, `deploy/**`, or any other existing source tree. | (a) Open remediation PRs alongside findings. (b) Author security-regression tests inline. (c) Adjust `.yarnrc.yml` to remove the accepted advisory. | CRITICAL Directive 1 frames the activity as an "audit" and the user annotation reads `~0 files modified`. Config A is the control measurement in a multi-config comparison study; mutating source would invalidate downstream parity against tool-augmented configurations. | If a finding is severe and a fix is obvious, the read-only stance defers remediation. This is accepted because remediation is out-of-scope for Config A and would prejudice subsequent comparison runs. |
| Adopt the four-lens methodology: (1) data-flow tracing, (2) call-chain inspection, (3) configuration review, (4) dependency declaration inspection. | (a) Pure data-flow taint analysis only. (b) Pure dependency-CVE inspection only. (c) Adopt a published framework checklist (OWASP ASVS) verbatim. | A single-lens analysis would systematically miss whole classes of weaknesses. Configuration and dependency findings rarely surface from pure data-flow tracing; data-flow-only sinks rarely surface from dependency manifests. The four lenses are orthogonal and additively cover the directive's surface ("trace data flows, follow call chains, examine configuration, and inspect dependency declarations"). | Some categories (e.g., business-logic flaws, complex authorization composition) sit at the intersection of multiple lenses and may be under-counted if a single lens dominates investigation time. |
| Conduct discovery using only native agent analysis — no Snyk, Semgrep, CodeQL, npm audit, Trivy, Grype, OSV-Scanner, Bandit, ESLint security plugins, or any other commercial/OSS SAST/SCA/DAST tool. | (a) Run `yarn npm audit` and ingest its JSON. (b) Spin up a Semgrep ruleset over the workspaces. (c) Use CodeQL via GitHub Advanced Security. | This is the definition of Config A (bare-baseline). The user constraint is verbatim: "using only native agent analysis — no external scanning tools." Invoking any tool would convert Config A into a different configuration and destroy the comparison. | Native analysis cannot match a mature scanner's transitive-dependency CVE coverage. The audit compensates by inspecting `package.json` resolutions, `yarn.lock` cross-references, and inherent agent knowledge of common CVEs (CWE-1104 family). Unknown-unknowns are an accepted Config A risk and the explicit point of the comparison. |
| Calibrate `severity` to CVSS v3.1 base-score bands where published CVSS data exists for a finding; otherwise calibrate qualitatively via (exploitability × blast-radius × reversibility). | (a) Pure qualitative severity. (b) Map directly to the MITRE CWE Top-25 rank. (c) Use OWASP Risk Rating Methodology end-to-end. | The four-value vocabulary `{critical, high, medium, low}` aligns naturally with CVSS bands (9.0–10.0 / 7.0–8.9 / 4.0–6.9 / 0.1–3.9). For dependency-CVE findings this is deterministic. For source-code findings without published CVSS, qualitative anchoring keeps the band semantics consistent across the comparison study. | CVSS bands embed assumptions (network attack vector default, no compensating controls) that may not reflect the deployed `blitzy-cal` environment. Severity is therefore an analyst estimate, not a contractual SLA. |
| Prefer CWE leaf nodes over parent categories — e.g., CWE-321 (hard-coded cryptographic key) over CWE-798 (hard-coded credentials) when the secret is specifically a cryptographic key; CWE-89 (SQL injection) over CWE-707 (improper neutralization). | (a) Always use the broadest parent CWE for resilience to taxonomy reorgs. (b) Always use the CWE-25 entry closest in spirit. (c) Use the deepest leaf even at low classification confidence. | The directive states "the most specific CWE you are confident about." Leaf nodes carry maximal information for downstream comparison. The clause "you are confident about" gates depth: when confidence in a leaf collapses, the audit falls back to a parent rather than guess. | Two analysts could pick different sibling leaves for the same observation; downstream tooling that aggregates by CWE may show small distribution drift across runs. Section 3 documents each non-obvious selection. |
| Sort findings deterministically by `(severity DESC, file ASC, line ASC)` before serialization. Severity uses the numeric ranking `critical=4, high=3, medium=2, low=1`. | (a) Sort by file path only. (b) Sort by CWE numerically. (c) Preserve discovery order. | Config A must be byte-reproducible on an unchanged codebase to be a meaningful baseline. Discovery-order or CWE-numeric sorting both fail this. Severity-first surfaces the most consequential findings at the top of the array, aiding downstream review tooling that may apply `head -n` previewing. | Adding/removing a single finding shifts subsequent positions and creates a noisy diff. Accepted because the artifact's primary consumer is a comparison tool that operates on the JSON document as a set, not as an ordered transcript. |
| Omit findings whose CWE classification confidence is low; do not inflate findings to reach a quota. Traceability matrix is N/A because this is a security audit, not a migration or refactor. | (a) Include all suspicious observations with `cwe: "CWE-UNKNOWN"`. (b) Include but mark `severity: low` for low-confidence cases. (c) Produce a separate "advisories" file alongside the schema. | The directive explicitly says "the most specific CWE you are confident about," which licenses omission over guesswork. The schema is closed (exactly five fields, no `confidence` field) so a low-confidence flag cannot be carried. The Explainability rule's traceability-matrix clause is conditioned on migration/refactor work and does not apply to audits. | Genuine but hard-to-classify weaknesses (novel patterns, business-logic flaws) may be missed. This is documented per-class in Section 6 (verified-safe constructs) and is the intentional trade-off behind the conservatism policy. |
| Write `findings-config-a.json` with exactly one trailing `\n` byte so that `wc -l < findings-config-a.json` reports `1`. The JSON tokens themselves remain whitespace-free (no `\n` between elements, no indent). | (a) Zero trailing bytes — content ends at `]`. (b) Trailing newline plus pretty-printing. (c) `\r\n` line ending. | The pass/fail gate `cat findings-config-a.json \| wc -l` returns `1` requires that exactly one newline character exist in the file (POSIX `wc -l` counts `\n` bytes). A file ending at `]` with no `\n` yields `wc -l == 0` and fails the gate. AAP §0.5.4 originally read "no trailing newline" via `sys.stdout.buffer.write`; the operational reading of the pass/fail gate supersedes the literal phrasing. See Section 4 row 4.2 for the explicit deviation entry. | A consumer expecting strict zero-byte-after-`]` would see one extra byte. Accepted because the user-stated pass/fail gate is the authoritative contract and every standard JSON parser ignores trailing whitespace. |

The policy fixes the chosen CWE so `findings-config-a.json` rows are consistent. Per-finding traceability is preserved through the `file` + `line` + `cwe` fields of each affected row in `findings-config-a.json`; the source-tree region cited inline below scopes which findings the policy governs.

(b) CWE-259 (Use of Hard-coded Password). (c) CWE-547 (Use of Hard-coded, Security-relevant Constants). | CWE-321 is technically a sibling leaf but applies most cleanly when the key is in source code. Both ARGs serve as "credentials" for keyed primitives, not strictly cryptographic-only keys. | A reviewer applying CWE-321 leaf-preference strictly might re-classify. ## Section 7 — Audit Methodology Justification

This section narrates how each of the four lenses was applied and what types of findings each produced. It complements Section 1 row 2 (the methodology adoption decision) and provides the operational receipt.

### Lens 1 — Data-flow tracing

**Sources considered:** HTTP request body, query parameters, path parameters, headers (including `X-Forwarded-*` and `Host`), cookies, OAuth callback parameters, webhook payload fields, environment variables read at request-handler granularity, and DB-stored content that originated as user input.

**Sinks considered:** Prisma `$queryRawUnsafe` / `$executeRawUnsafe` (parameter-aware), `child_process.exec*`, `fs.*` operations on caller-supplied paths, outbound `fetch`/`axios`/`got`/`node-fetch` with caller-supplied URLs, response body composition (including JSON shape and HTML rendering), `Location:` redirect targets, `dangerouslySetInnerHTML` and similar React escape hatches, `eval`/`new Function`/`setTimeout(string)`, template engines (Handlebars in webhook payload signing).

**Representative findings produced (citing actual `findings-config-a.json` rows):** SSRF on outbound webhook dispatch (CWE-918 at `packages/features/webhooks/lib/sendPayload.ts:373`), open redirect via unsanitized return-to cookie (CWE-601 at `apps/web/proxy.ts:86`), reflected XSS sink coverage (CWE-79 at `apps/web/modules/signup-view.tsx:349` and `packages/emails/src/components/RawHtml.tsx:5`), spoofable IP-source headers (CWE-348 at `packages/lib/getIP.ts:17`), credential disclosure in debug logs (CWE-532 at `packages/features/auth/lib/next-auth-options.ts:151`).

**Method:** Static call-graph walk from each handler entry point through service-layer composition, flagging untyped boundaries and `any`-typed inputs that escape Zod schema enforcement.

### Lens 2 — Call-chain inspection

**Targets:** NextAuth provider registration and callback chain (`packages/features/auth/lib/next-auth-options.ts`), API v2 NestJS guard ordering (`@UseGuards(ApiAuthGuard, PermissionsGuard, PbacGuard, CustomThrottlerGuard)`), tRPC procedure middleware composition, Prisma extension coverage on sensitive mutations (`disallow-undefined-delete-update-many`, `exclude-locked-users`), audit-trail emission for impersonation, role changes, credential rotation, and watchlist updates.

**Representative findings produced (citing actual `findings-config-a.json` rows):** Broken/risky hash for password derivation (CWE-916 at `packages/trpc/server/routers/viewer/organizations/setPassword.handler.ts:36` — MD5 over email+key), broken hash function for TOTP cryptographic seeds (CWE-327 at `packages/features/auth/lib/verifyCodeUnAuthenticated.ts:17`, `packages/features/auth/lib/verifyEmail.ts:100`, `packages/trpc/server/routers/viewer/organizations/verifyCode.handler.ts:54`, `packages/trpc/server/routers/viewer/workflows/verifyEmailCode.handler.ts:24`), missing constant-time HMAC compare in webhook handler (CWE-208 at `packages/app-store/hitpay/api/webhook.ts:107`), missing explicit JWT algorithm allow-list (CWE-347 at `packages/features/auth/lib/oAuthAuthorization.ts:9`), key reuse across distinct cryptographic algorithms (CWE-1240 at `packages/features/auth/lib/oAuthAuthorization.ts:9`).

**Method:** Decorator-presence checks against the documented PBAC-required surface; cross-file follow-through to confirm that `canEditEntity`/`canAccessEntity` are reached before any state mutation; tracing each cryptographic primitive call back through helper composition to identify shared/weak keying material.

### Lens 3 — Configuration review

**Targets:** `Dockerfile`, `apps/api/v2/Dockerfile`, `docker-compose.yml`, `.env.example`, `.env.appStore.example`, `.yarnrc.yml`, `apps/web/next.config.ts`, `apps/api/v1/next.config.js`, all files under `.github/workflows/**` and `.github/actions/**`, `biome.json` (linter security rules), `app.json` (Heroku addons), `turbo.json` (env-var passing to remote cache).

**Representative findings produced (citing actual `findings-config-a.json` rows):** Hardcoded default ARG values in Dockerfile (CWE-798 at `Dockerfile:11` and `Dockerfile:12`), default DB credentials in compose / CI (CWE-798 at `docker-compose.yml:20`, `docker-compose.yml:21`, `.github/workflows/release-docker.yaml:9`), root user in container (CWE-250 at `Dockerfile:1` and `apps/api/v2/Dockerfile:26`), unpinned third-party GitHub Action (CWE-829 at `.github/workflows/i18n.yml:32`), unpinned major-version action tags (CWE-829 at `.github/workflows/i18n.yml:1`), permissive CORS configurations (CWE-942 at `apps/api/v1/lib/helpers/addRequestid.ts:10`, `apps/api/v2/src/bootstrap.ts:46`, `apps/web/pages/api/router/index.ts:8`), weakened CSP (CWE-693 at `apps/web/lib/csp.ts:22`, `apps/web/next.config.ts:434`, `apps/web/proxy.ts:65`), default SAML client-secret verifier (CWE-1188 at `packages/features/ee/sso/lib/saml.ts:15`).

**Method:** Direct file inspection plus cross-reference against AAP §0.2.3's documented existing controls so that "control already in place" cases are not double-counted as findings.

### Lens 4 — Dependency declaration inspection

**Targets:** Root `package.json` `resolutions` block, `apps/{web,api/v1,api/v2}/package.json`, all per-workspace manifests, `yarn.lock` (transitive truth), `.yarnrc.yml` accepted-advisory exception list, `.yarn/patches/*.patch`.

**Findings produced:** None emitted in this audit run. The pinned `resolutions` block in the root `package.json` (axios 1.13.5, lodash 4.17.23, jsonwebtoken 9.0.0, jws 4.0.1, qs 6.14.1, node-forge 1.3.2, validator 13.15.22, tar 7.5.7, form-data 4.0.4) is current relative to inherent agent knowledge of CVE-affected ranges, and the documented exception (`fast-xml-parser@4.4.1` via `.yarnrc.yml npmAuditIgnoreAdvisories`) is honored per Deviation 4.3. The CWE-1104 (Use of Unmaintained Third-Party Components) category catalog row remains in Section 3 as the policy rule that *would* govern any such finding if one were identified; the audit's confidence threshold (Section 1 row 7) is the gating reason no CWE-1104 row appears in `findings-config-a.json`. Note: Config A's read-only stance plus no-external-scanners constraint (Section 1 row 3) accepts the known limitation that some transitive-only CVEs are not surfaced without an SCA tool — this is the explicit trade-off underpinning the multi-config comparison study.

**Method:** Cross-reference pinned versions against inherent agent knowledge of CVE-affected version ranges. The accepted `fast-xml-parser@4.4.1` advisory is excluded per Deviation 4.3. No external network calls and no scanner invocations are performed.

### Why these four lenses, and not five or three?

Three lenses (omitting configuration) systematically miss container, CI, and environment-template findings — historically a major source of supply-chain and secret-leak incidents. Five lenses (adding e.g., a "business-logic" lens) introduce ambiguity at the lens boundary because business-logic findings cleanly decompose into data-flow + call-chain + authorization concerns already covered by Lenses 1–2. The four-lens partition is orthogonal and additively complete for the directive's stated surface.

## Section 8 — Reproducibility Statement

Config A is defined as the bare-baseline control measurement of a multi-config comparison study. Reproducibility is a first-class requirement: re-running the same audit on the same codebase snapshot with the same agent should yield the same `findings-config-a.json` byte content (modulo sort-stable equivalents).

### Verification commands

The following commands verify the pass/fail gate for `findings-config-a.json`:

1. **Single-line check** (must return exactly `1`):
   `cat findings-config-a.json | wc -l`

2. **Valid-JSON check** (must exit `0`):
   `python3 -m json.tool findings-config-a.json > /dev/null`

3. **Schema-conformance assertion** (must exit `0`):
   `python3 -c "import json; arr=json.load(open('findings-config-a.json')); assert isinstance(arr, list); assert all(set(o.keys())=={'file','line','severity','cwe','description'} and isinstance(o['line'], int) and o['severity'] in {'critical','high','medium','low'} and len(o['description'])<=200 and isinstance(o['cwe'], str) and o['cwe'].startswith('CWE-') for o in arr)"`

4. **Determinism check** (sort-stable re-emission must equal original):
   `python3 -c "import json; arr=json.load(open('findings-config-a.json')); rank={'critical':4,'high':3,'medium':2,'low':1}; assert arr == sorted(arr, key=lambda o:(-rank[o['severity']], o['file'], o['line']))"`

### Determinism levers

Three properties of the audit pipeline together ensure byte-stable output:

- **Sort order:** `(severity DESC, file ASC, line ASC)` — Section 1 row 6.
- **CWE selection policy:** Section 3 catalogs every near-equivalent choice so that re-application of the same rules produces the same CWE assignment.
- **Confidence threshold:** Section 1 row 7 — low-confidence findings are omitted rather than guessed; the omission decision is stable across runs because confidence is grounded in observed code, not stochastic inference.

### Reproducibility caveats

The audit's findings depend on:

- The agent's inherent knowledge of CVE-affected version ranges at the time of execution. A future agent with refreshed knowledge may classify additional `CWE-1104` entries.
- The codebase snapshot — any commit affecting `apps/**`, `packages/**`, `scripts/**`, `Dockerfile`, `docker-compose.yml`, `package.json`, `yarn.lock`, `.yarnrc.yml`, or `.github/workflows/**` may shift the findings set.
- The CWE catalog version — MITRE periodically renumbers / re-organizes the catalog. The audit references the stable Top-25 leaf identifiers and is robust to most updates.

### What is not part of reproducibility

- The exact textual phrasing of `description` fields within the 200-character budget. Different agent runs may select different wordings; the schema integrity contract (5 fields, severity vocabulary, CWE pattern, ≤200 chars) holds regardless.
- The exact line number when a finding spans multiple lines. The "most representative single line" rule (typically the sink line or the declaration line) admits modest variation; consumers should treat `line` as a navigation hint rather than a primary key.
