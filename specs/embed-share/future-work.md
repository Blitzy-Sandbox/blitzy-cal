# Embed & Share Future Work

Ideas and enhancements deferred from the Sprint 6: Embed & Share initial implementation.

## Enhancements

- **EMB-001**: Platform-specific embed integration guides for WordPress, Shopify, Squarespace, Wix, Webflow, Weebly, and Joomla — documentation-only item not in EM epic scope. Create integration guides in Mintlify documentation covering platform-specific setup, including WordPress plugin embedding via custom HTML blocks or shortcodes, Shopify theme integration through the Online Store theme editor, and Squarespace custom code block usage with the `embed-snippet` loader. Each guide should reference the existing `@calcom/embed-snippet` package as the recommended integration path.
- **EMB-002**: Pure iframe fallback documentation — document a basic `<iframe src="https://app.cal.com/user/event/embed">` approach for platforms that restrict JavaScript execution. This covers environments where Content Security Policy headers or platform sandboxing prevent loading external scripts, making the full `embed-snippet` or `embed-core` packages unusable. The iframe fallback lacks prefill support, event tracking, auto-resize, and hide-details capabilities, so the documentation should clearly note these trade-offs. Not in EM epic scope.
- **EMB-003**: Skeleton loader expansion to `week_view` layout — implement skeleton loaders for the week view layout type to complete layout coverage beyond the currently supported responsive, mobile, and `month_view` layouts. This is a Cal.com advantage refinement (Calendly has no skeleton loaders at all) rather than a Calendly parity gap.
- **EMB-004**: Skeleton loader expansion to `column_view` layout — implement skeleton loaders for the column view layout type to complete the full set of layout skeleton coverage. This is a Cal.com advantage refinement, not a Calendly parity gap.
- **EMB-005**: Booking form skeleton shows slots skeleton instead of form-specific skeleton — create a form-specific skeleton loader for `*.event.booking.form` page types (`user.event.booking.form` and `team.event.booking.form`). Currently these page types fall back to displaying the slots skeleton, which does not match the actual form layout. This is a Cal.com advantage refinement, not a Calendly parity gap.
- **EMB-006**: ModalBox iframe reuse re-enablement — resolve stale UI issues that caused ModalBox iframe reuse to be disabled, to improve repeat modal opening performance. The prerendering system defines four reuse actions (`noAction`, `connect-no-slots-fetch`, `connect`, `fullReload`) but iframe reuse is currently disabled as a workaround. Re-enabling this optimization would provide near-instant modal reopening for users who repeatedly open and close the booking modal.
- Skeleton loader for `user.profile` and `team.profile` page types — extend skeleton loader coverage to profile pages for a consistent loading experience across all embeddable page types. Currently only `*.event.booking.slots` page types have skeleton support, leaving profile pages with a blank or spinner loading state that contrasts with the polished skeleton experience on booking pages.
- Advanced embed analytics dashboard — track embed impressions, conversion rates, and user engagement metrics across all three embed types (inline, modal, floating button). Leverage the existing 14+ embed lifecycle events (`bookerViewed`, `bookerReady`, `linkFailed`, etc.) to provide aggregated analytics to Cal.com users, enabling data-driven optimization of their embedded booking flows.

## Technical Debt

- Consolidate shared embed initialization logic between `Cal.inline()`, `Cal.modal()`, and `Cal.floatingButton()` to reduce code duplication in `packages/embeds/embed-core/src/embed.ts` — each embed method currently implements its own iframe creation, handshake initialization, and command queue management with subtle variations that could diverge over time
- Standardize error handling across embed types — currently error reporting varies between inline (linkFailed event), modal (error state), and floating button (silent fallback), making it difficult for integrators to implement consistent error recovery across embed types
- Extract shared postMessage message parsing and validation into a standalone utility to be reused across embed-core and any future embed packages — the message originator check (`originator: "CAL"`), payload type discrimination, and dimension parsing logic are currently inlined in the embed runtime
- Investigate and document the ModalBox iframe reuse stale UI issues (EMB-006) for potential resolution in a future sprint — capture the specific scenarios that cause stale state (configuration drift, slot staleness threshold exceeded, path mismatches) to provide a clear remediation path

## Nice to Have

- Visual embed configuration builder in the Cal.com web UI with live preview for all three embed types — allow users to configure embed appearance (theme, layout, prefill fields, button text, button position) through a point-and-click interface and generate the corresponding `embed-snippet` or `embed-react` code automatically
- Embed performance monitoring dashboard showing load times, handshake completion rates, and error rates per embed type — provide visibility into embed health across all deployed instances, surfacing slow handshakes, high `linkFailed` rates, or dimension change storms that indicate integration issues
- Server-side rendering support for embed-react component to improve SEO for pages with embedded booking widgets — currently the `Cal` React component renders client-side only, meaning search engine crawlers see an empty container rather than booking page content
- Multi-embed orchestration patterns — document and test common patterns for coordinating multiple embed instances on a single page (e.g., routing form → booking page flow), including namespace management strategies, inter-embed event forwarding, and shared configuration patterns for pages that display multiple Cal.com embeds simultaneously
