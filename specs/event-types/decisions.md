# Event Types (Sprint 2) Decisions

## ADR-001: Schema Columns vs. Metadata-Based Approaches for Parity Fields

### Context

Sprint 2 event type parity closure (epics ET-001 through ET-006) may require storing additional configuration data for which the `EventType` Prisma model does not currently have a dedicated column. The `EventType` model is already one of the largest models in the Cal.com schema with 85+ scalar fields (100+ including relations) spanning scheduling configuration, booking constraints, host assignment, buffer times, custom fields, and more. It also includes a flexible `metadata` column (`Json?`) that is parsed and validated at the application layer by the `EventTypeMetaDataSchema` Zod schema defined in `packages/prisma/zod-utils.ts`. This metadata field is an established pattern in Cal.com for storing evolving, app-specific, and feature-flag-gated configuration without requiring a database migration. Meanwhile, the zero-downtime migration rules documented in `docs/migration/zero-downtime-strategy.mdx` strictly require additive-only schema change patterns: new columns must be nullable with defaults, column renames and type changes are forbidden, and `NOT NULL` additions without defaults are never permitted. Given these constraints, a decision is needed on where to store any new parity-specific configuration that may be identified during Sprint 2 implementation — as dedicated schema columns requiring a Prisma migration, or within the existing metadata JSON field validated by Zod.

### Options Considered

1. **Add dedicated schema columns** — Add new nullable columns to the `EventType` model for each parity field identified during Sprint 2 closure.
   - Pros: Type-safe at the database level with PostgreSQL constraints; queryable via standard Prisma `where` clauses without raw SQL; provides clear, self-documenting schema; enforced by database-level NOT NULL, CHECK, and default constraints; visible in Prisma Studio and database inspection tools.
   - Cons: Requires a new Prisma migration file in `packages/prisma/migrations/`; adds to the already large `EventType` model (85+ scalar fields); must strictly follow zero-downtime additive-only patterns (nullable columns with defaults only); increases migration count beyond the current 585+ chronological migrations; every new column adds overhead to `SELECT *` queries even when unused.

2. **Use metadata JSON field** — Store parity-specific fields in the existing `metadata` (`Json?`) column, validated by `EventTypeMetaDataSchema` (Zod) at the application layer.
   - Pros: No database migration needed — zero risk to production deployments; flexible schema evolution without DDL changes; validated at the application layer via Zod with full TypeScript type inference; already an established and well-understood pattern in Cal.com (used for Stripe pricing, app-specific settings, and feature flags); supports incremental rollout behind feature flags without schema commitment.
   - Cons: Not queryable via standard Prisma `where` filters without raw SQL or JSON operators; no database-level type enforcement — schema drift is possible if Zod validation is bypassed; metadata fields are opaque to database tooling and Prisma Studio; performance implications for large JSON payloads on high-traffic queries; harder to enforce uniqueness or referential integrity constraints.

### Decision

Use a hybrid approach — leverage existing dedicated columns where they already exist in the schema and only use the metadata field for truly new parity-specific flags that do not warrant a permanent schema addition. The `EventType` model already contains dedicated columns for all major parity-relevant configurations: `seatsPerTimeSlot` (group events, ET-002), `isRRWeightsEnabled` and `rrSegmentQueryValue` (round-robin distribution, ET-003), `schedulingType` with the `SchedulingType` enum covering `ROUND_ROBIN`, `COLLECTIVE`, and `MANAGED` (ET-003, ET-004), `periodType` with the `PeriodType` enum covering `UNLIMITED`, `ROLLING`, `ROLLING_WINDOW`, and `RANGE` along with `periodDays`, `periodStartDate`, `periodEndDate`, and `periodCountCalendarDays` (booking windows, ET-005), `bookingFields` (custom fields, ET-006), `minimumBookingNotice`, `beforeEventBuffer`, `afterEventBuffer` (buffer times), and `assignAllTeamMembers` and `assignRRMembersUsingSegment` (host assignment). Given this comprehensive existing schema coverage, Sprint 2 parity closure is expected to require zero or minimal new columns. Any truly new configuration flags that emerge during implementation — particularly those that are experimental, feature-flag-gated, or only relevant to a small subset of event types — should be stored in the metadata field with corresponding Zod validation in `EventTypeMetaDataSchema`. This minimizes migration risk while maintaining type safety for all critical scheduling fields.

### Consequences

- Existing event type behavior is fully preserved — no migration risk for the vast majority of parity fields, which already have dedicated schema columns.
- Any truly new fields added via metadata must have corresponding Zod validation added to `EventTypeMetaDataSchema` in `packages/prisma/zod-utils.ts` to prevent schema drift and ensure type safety at the application boundary.
- If a metadata field becomes frequently queried (e.g., used in `WHERE` clauses for slot generation or availability computation), a future migration should be planned to promote it to a dedicated column following the zero-downtime additive-only pattern documented in `docs/migration/zero-downtime-strategy.mdx`.
- Sprint 2 implementation should audit each epic's data requirements against the existing `EventType` schema before proposing any new columns or metadata fields — the goal is to maximize use of existing infrastructure.
- This decision aligns with Cal.com's proven migration approach across 585+ chronological migrations: add columns only when they serve a permanent, widely-used purpose; use metadata for evolving or experimental configuration.

## ADR-002: Round-Robin Distribution Algorithm Fairness Approach

### Context

Cal.com's round-robin distribution system uses `SchedulingType.ROUND_ROBIN` on the `EventType` model with several advanced configuration options: configurable host weights via the `isRRWeightsEnabled` boolean flag and per-host `weight` fields on the `Host` model, host priority via the `priority` field on the `Host` model, and segment-based filtering via `assignRRMembersUsingSegment` and `rrSegmentQueryValue` which allow attribute-based host selection. The round-robin implementation in `packages/features/ee/round-robin/` includes booking management, rescheduling, reassignment, host priority/weight calculation, slot validation, and assignment reason recording. Calendly's round-robin, by contrast, distributes bookings "equitably" among team members with a simpler model that does not expose host weights, priority levels, or segment-based filtering. Cal.com already exceeds Calendly's round-robin capabilities — the gap report in `docs/gap-report/event-types.mdx` identifies this as a Cal.com advantage (6 scheduling paradigms vs. Calendly's 4, plus segment-based round-robin). The decision needed is how to verify and align core distribution fairness for parity validation (ET-003, ET-VAL-003) while preserving Cal.com's advanced round-robin capabilities that existing users depend on.

### Options Considered

1. **Simplify to match Calendly exactly** — Implement strict equal-distribution logic that matches Calendly's simpler round-robin model, potentially disabling or deprecating the advanced weight, priority, and segment features.
   - Pros: Guarantees exact Calendly behavioral parity for round-robin distribution; simpler validation — only need to verify equal distribution across hosts; reduces code complexity in the round-robin module.
   - Cons: Removes Cal.com's documented advantage over Calendly (weights, priorities, segments); constitutes a breaking change for existing users who rely on advanced round-robin features like `isRRWeightsEnabled` and `rrSegmentQueryValue`; contradicts the gap report's finding that Cal.com exceeds Calendly in this area; would require deprecation notices and migration paths for affected users; reduces Cal.com's competitive differentiation.

2. **Verify existing fairness, preserve advantages** — Audit the existing round-robin distribution logic in `packages/features/ee/round-robin/` to confirm that equitable baseline distribution occurs when weights are equal or disabled (the default configuration), while preserving Cal.com's advanced weight, priority, and segment capabilities as documented advantages over Calendly.
   - Pros: Maintains full backward compatibility — no behavioral changes for any existing users; preserves Cal.com's competitive advantages (6 scheduling paradigms vs. Calendly's 4, segment-based RR, weighted distribution); validates Calendly parity at the behavioral level — when `isRRWeightsEnabled` is `false` (the default), distribution matches Calendly's equitable model; aligns with the gap report's assessment that Cal.com exceeds Calendly in round-robin capabilities.
   - Cons: More complex validation required — must test both the default equitable scenario and the advanced weighted/priority/segment scenarios; parity tests must carefully isolate the default behavior from the advanced features; documentation must clearly distinguish between "Calendly-equivalent baseline" and "Cal.com advanced features".

### Decision

Option 2 — verify existing fairness and preserve Cal.com's advantages. When `isRRWeightsEnabled` is `false` (the default for all new event types), the round-robin distribution algorithm must produce equitable assignment across all available hosts, matching Calendly's documented behavior for ET-VAL-003. When weights and priorities are enabled, Cal.com's advanced distribution capabilities — including per-host weight allocation, priority-based ordering, segment-based filtering via `rrSegmentQueryValue`, `rescheduleWithSameRoundRobinHost` behavior, `includeNoShowInRRCalculation`, and `rrHostSubsetEnabled` — are preserved as documented advantages that exceed Calendly's feature set. Validation tests must cover both scenarios: (a) default equitable distribution with equal/no weights confirming Calendly parity, and (b) advanced weighted distribution confirming Cal.com's extended capabilities continue functioning correctly.

### Consequences

- Existing round-robin users experience no behavioral changes — full backward compatibility is maintained for all configurations (default equitable and advanced weighted).
- Parity tests for ET-003 must verify equitable distribution with default settings to satisfy ET-VAL-003 acceptance criteria, ensuring that when `isRRWeightsEnabled` is `false`, each host receives a fair share of bookings over time.
- Advanced round-robin features (weights via `isRRWeightsEnabled`, priorities via `Host.priority`, segments via `rrSegmentQueryValue`, same-host rescheduling via `rescheduleWithSameRoundRobinHost`) are documented as Cal.com advantages in the gap report at `docs/gap-report/event-types.mdx` and preserved without modification.
- The RR Fairness Cap Visualization enhancement identified as a Low priority gap (ET-002 in the gap report) is deferred to `specs/event-types/future-work.md` as it represents a UI analytics enhancement rather than a behavioral parity requirement.
- Any future changes to the round-robin algorithm must maintain the equitable baseline behavior when weights are disabled, as this is now a documented parity guarantee validated by Sprint 2 acceptance criteria.
